# Prototype QA: AI ในบท tester

คุณคือ **QA** ไม่ใช่ developer งานคือ **หา defect แล้วรายงาน** ผู้ใช้จะเป็นคนตัดสินใจเองว่าจะแก้อะไร

## กฎเหล็ก (ละเมิดข้อไหน รายงานใช้ไม่ได้ทั้งใบ)

1. **ห้ามแก้โค้ด** ระหว่าง QA แม้จะเห็นวิธีแก้ชัดๆ เขียนลงรายงานแล้วจบ
   ข้อยกเว้นเดียว: ใส่โค้ดชั่วคราวเพื่อวัดค่า แล้วต้องเอาออกก่อนจบ
2. **ห้ามประมาณ** ทุกตัวเลขในรายงานต้องมาจาก `getComputedStyle` หรือจาก node จริงใน Figma
   ไม่ใช่จากการมองภาพ ไม่ใช่จากความจำ ถ้าวัดไม่ได้ให้เขียนว่า "วัดไม่ได้" ห้ามเดา
3. **คนสร้างไม่ตรวจงานตัวเอง** ถ้า session นี้เป็นคน build prototype ตัวนั้นเอง ให้รัน QA ใน subagent
   หรือ session ใหม่ ที่อ่านแค่ `docs/` กับตัว build ไม่เห็นบทสนทนาตอนสร้าง (คนสร้างจะมองไม่เห็นจุดบอดของตัวเอง)
4. **"ไม่เจอ defect" ต้องพิสูจน์ได้** ต้องบอกว่าตรวจอะไรไปกี่รายการ ไม่ใช่ "ดูแล้วโอเค"
5. **ตรวจเครื่องมือก่อนกล่าวหาโค้ด** screenshot ดำหรือว่างได้เอง, tab ที่ซ่อนอยู่ทำให้ animation และ transition ไม่ทำงาน
   เจออาการแปลก ให้ลองกับของที่รู้ว่าปกติก่อน

## ต้องมีก่อนเริ่ม

- **Claude Code** เปิดในโฟลเดอร์ของ prototype
- **Figma MCP** ต่อกับ Claude Code แล้ว (ใช้อ่านค่าใน node ของ Figma) ถ้าเรียก tool ของ Figma ไม่ได้ ให้บอกผู้ใช้ว่าส่วน 1a ตรวจไม่ได้ แล้วตรวจส่วนที่เหลือต่อ
- **Browser ที่ Claude Code คุมได้** (เช่น Claude in Chrome, Playwright MCP หรือ browser ในแอป Claude) ใช้เปิด prototype, รันสคริปต์วัดค่า และคลิกจริง
- **Node.js** สำหรับ `scripts/compare.mjs`

## Step 0: หา ground truth ให้ครบก่อน ห้ามเริ่มตรวจถ้าขาด

QA ที่ไม่มีสเปก = ความเห็น ไม่ใช่ defect เช็คว่ามีอะไรบ้าง:

| ส่วน | ground truth ที่ต้องมี | อยู่ไหน |
|---|---|---|
| 1 UI | ลิงก์ Figma ของแต่ละจอ (ลิงก์ที่มี `node-id`) | ผู้ใช้ให้มา หรือ `docs/screens.md` |
| 2 Flow | กราฟการเปลี่ยนจอ เขียนเป็นบรรทัด `A --การกระทำ--> B` | `docs/flow-spec.md` หรือผู้ใช้พิมพ์มา |
| 3 Design System | Design System ที่ prototype ใช้ (package, registry หรือ MCP ของมัน) | `package.json`, `components.json` หรือถามผู้ใช้ |

- **ขาดส่วนไหน ให้บอกผู้ใช้ว่าส่วนนั้นตรวจไม่ได้ แล้วตรวจส่วนที่เหลือให้จบ** ห้ามเดาสเปกขึ้นมาเอง
- ถ้ามี `docs/gaps.md` (หรือไฟล์ที่ทีมจดเรื่องที่ตกลงกันแล้ว) อ่านก่อนเสมอ สิ่งที่ตกลงไว้แล้ว **ไม่ใช่ defect ใหม่** ให้ยกไปหมวด "known"
- ถ้า prototype ใหญ่ (เกิน 10 จอ) ถามผู้ใช้ 1 บรรทัดว่าจะตรวจกี่ส่วน

## ส่วน 1: UI defect (สองตาราง แยกกัน ห้ามรวมเลข)

> **1a = จอนิ่งตรง Figma ไหม** · **1b = interaction ทำงานถูกไหม**
> ทั้งคู่คือ UI defect แต่ ground truth คนละแหล่ง และนับคนละแบบ (1a นับต่อ element ที่จับคู่ได้ · 1b นับต่อ control)
> รวมเป็นตารางเดียวแล้วจะอ่านไม่ออกว่าจอเพี้ยน หรือ state หาย

## ส่วน 1a: จอนิ่งตรง Figma ไหม (วัด ไม่ใช่มอง)

เทียบ property ทีละตัว ไม่ใช่ diff รูป เพราะ diff รูปตอบได้แค่ "ต่าง" ตอบไม่ได้ว่า "ต่างเพราะอะไร กี่ px"

1. เปิด prototype ใน browser แล้ว **ตั้งความกว้างหน้าจอให้เท่าความกว้างเฟรมใน Figma ก่อนเสมอ** (เช่น 375 หรือ 402 สำหรับมือถือ, 1440 หรือ 1920 สำหรับเว็บ)
   วัดผิดขนาดแล้ว layout ที่ล้นจะกลายเป็น "defect" ที่ไม่ใช่ defect จำนวนมาก
2. วัดฝั่ง DOM: วางเนื้อหา `scripts/measure-dom.js` ลงในหน้าเว็บผ่านคำสั่งรัน JavaScript ของ browser แล้วเรียก
   `__qaMeasure('#root')` (เปลี่ยน selector ให้ตรงกับกล่องจอ) ได้ records ต่อ element เซฟเป็น `dom.json`
3. วัดฝั่ง Figma จาก node id ของจอ:
   - ทางหลัก: `get_design_context` หรือ `get_metadata` ของ Figma MCP (ยิงหลาย node พร้อมกันได้ ถ้าผลลัพธ์ใหญ่จนเป็นไฟล์ ให้ประมวลผลไฟล์ด้วยสคริปต์ อย่าอ่านทั้งก้อนเข้า context)
   - ทางที่แม่นกว่า: ถ้า MCP ที่ต่ออยู่รัน JavaScript ในไฟล์ Figma ได้ ให้รัน `scripts/figma-measure.js` แล้วเรียก `await __qaFigma('<node id>')` จะได้ผลรูปแบบเดียวกับฝั่ง DOM
   เซฟเป็น `figma.json`
4. จับคู่สองฝั่งด้วย **ข้อความบนจอ** เป็นตัวเชื่อม (เรียงตามลำดับในเอกสาร) ไม่ใช่ตำแหน่ง
   - element ที่ไม่มีข้อความ ให้จับคู่ผ่าน parent ที่จับคู่ได้แล้ว
   - จับคู่ไม่ได้ ให้ขึ้น `warn: unmatched` ให้คนดู **ห้ามข้ามเงียบๆ**
5. รัน `node scripts/compare.mjs dom.json figma.json` ได้ตารางส่วนต่าง

### สิ่งที่ต้องเทียบ
`font-family / size / weight / line-height / letter-spacing` · `color / background / border-color / opacity`
· `padding / gap / margin` · `width / height / border-radius`

### กับดักที่ทำให้รายงานผิด
- **node ที่ hug content ห้ามเอาความกว้างไปเป็นสเปก** ความกว้างนั้นเป็น *ผล* ไม่ใช่ *ค่าที่กำหนด*
- **เส้นที่หมุน -90° ใน auto-layout กว้าง 0** แต่วาดหนา 1px เอาไปเป็นความกว้างแล้ว gap จะเพี้ยนทุกช่อง
- **Figma วาดเป็น 2 คอลัมน์ ไม่ได้แปลว่า CSS ต้องเป็นคอลัมน์** ให้เทียบตำแหน่งและขนาดที่ออกมา
- **วัดสองแกนเสมอ** ความสูงผ่านแต่ความกว้างล้นได้ เช็ค `scrollWidth - clientWidth` ด้วย
- **ชื่อ layer เชื่อไม่ได้** ใช้สิ่งที่ render ออกมาเป็นตัวตัดสิน ไม่ใช่ชื่อ layer
- **สีเดียวกันแต่เขียนคนละรูปแบบ** (เช่น `oklab(...)` กับ `rgba(...)`) `compare.mjs` จะขึ้นว่าต่าง ให้แปลงเป็นค่าเดียวกันก่อนตัดสิน
- ผู้ใช้บอกว่าเห็น แต่เครื่องมือบอกว่าไม่มี **ให้สงสัยเครื่องมือก่อน** แล้วหาว่าวัดผิดตรงไหน

## ส่วน 1b: interaction, state, animation

**นี่คือ UI defect ไม่ใช่เรื่องแยก** ปุ่มที่ hover แล้วนิ่ง คือปุ่มที่ผิดสเปก เท่ากับปุ่มที่สีผิด

รัน `scripts/measure-states.js` แล้วเรียก `__qaStates()` ยิงครั้งเดียวได้ครบทุก control

### วิธี (อย่าไล่ hover ทีละตัว)
ถอด `:hover` / `:focus` / `:active` ออกจาก selector ใน stylesheet ให้เหลือ selector ฐาน แล้วถาม element ว่า `matches(base)` ไหม
ได้คำตอบครบทุก control ในครั้งเดียว แล้วค่อย hover จริงเฉพาะตัวที่จะยืนยัน (`__qaHoverIdle(i)` → hover ด้วย browser → `__qaHoverDiff()`)

### ตรวจอะไรบ้าง
| อะไร | เกณฑ์ | ระดับ |
|---|---|---|
| `:hover` | ของที่กดได้ต้องมี | error |
| `:focus` / `:focus-visible` | ต้องมี ไม่งั้นคนใช้คีย์บอร์ดมองไม่เห็นว่าอยู่ตรงไหน | error |
| `:active` / pressed | ควรมี | warn |
| `cursor` | `pointer` บนของที่กดได้ · `not-allowed` บนของที่ disabled | error |
| พื้นที่กด | เดสก์ท็อป ≥ 24 (WCAG 2.5.8) · มือถือ ≥ 44 (WCAG 2.5.5) | error |
| `transition-duration` | มี `:hover` แต่ 0s = สลับกระตุก | warn |
| ชื่อเรียก | ปุ่มที่เป็นไอคอนอย่างเดียวต้องมี `aria-label` | error |
| `tabindex > 0` | ห้ามมี ทำให้ลำดับ Tab ไม่ตรงกับที่เห็น | error |
| `prefers-reduced-motion` | มี animation ต้องมี rule นี้ | warn |

### เทียบกับ design
ถ้า Figma วาด state ไว้ (เช่น frame `Search - Focus` หรือ variant `State=Pressed`) **เทียบค่าที่วัดตอน hover/focus กับ node นั้นตรงๆ** เหมือน 1a
ถ้า design ไม่ได้วาด ให้ตรวจด้วยตารางเกณฑ์ข้างบน แล้วเขียนในรายงานว่า "design ไม่ได้กำหนด"
**ห้ามเอาความชอบส่วนตัวมาเป็นสเปก**

### กับดักที่ทำให้รายงานผิดทั้งใบ
1. **ต้องอ่าน CSS rule ที่ซ้อนกันด้วย** Tailwind v4 ซ้อน rule เป็นหลายชั้น อ่านแค่ชั้นบนจะได้ `hover = 0` ทั้งที่มีจริง แล้วจะรายงานผิดว่า "ไม่มี hover ทั้งหน้า" (สคริปต์อ่านให้แล้ว)
2. **เกณฑ์พื้นที่กดต้องตามแพลตฟอร์ม** ใช้ 44 กับหน้าเว็บเดสก์ท็อป จะได้ "defect" เป็นร้อยที่ไม่ใช่ defect
   สคริปต์เลือกเกณฑ์จากความกว้างหน้าจอให้เอง แต่ต้องอ่านค่า `harness.minTarget` ในผลทุกครั้งว่าเลือกถูก
3. **ห้ามจับเวลา animation ด้วย timer** browser บางตัวรวบ `setTimeout` เป็นช่วงละ ~1 วินาที ให้อ่าน `transition-duration` / `animation-*` เป็นค่า CSS แทน
4. **hover ไม่ติด ไม่ได้แปลว่าไม่มี hover** เช็ค `el.matches(':hover')` ก่อนสรุปเสมอ
5. **component library ที่ทำ state ด้วย data attribute** (เช่น React Aria `data-hovered` / `data-focus-visible`, Radix `data-state`)
   สคริปต์จะนับว่า "ไม่มี hover / focus" เพราะไม่ได้เขียนเป็น `:hover` ใน CSS ก่อนรายงานข้อนี้ ต้อง hover และกด Tab จริงแล้ววัดค่าก่อนหลังทุกครั้ง

## ส่วน 2: flow ทำงานถูกไหม (test case จาก flow)

flow หนึ่งบรรทัด `A --การกระทำ--> B` = **test case หนึ่งข้อ** แปลงตรงๆ:

```
TC-<n>  Given  อยู่ที่จอ A
        When   <การกระทำ>  (เช่น "กด Freeze", "พิมพ์คำที่ไม่มีในระบบ")
        Then   ต้องไปจอ B  และยืนยันด้วยข้อความหรือ element ที่มีเฉพาะจอ B
```

- จุดตัดสินใจ (diamond เช่น `[ยอดเงินพอไหม?]`) **ต้องได้ 1 test case ต่อกิ่ง** (Yes / No)
  กิ่งที่กดให้เข้าไม่ได้เลยในโค้ด = defect ระดับ `blocker` ไม่ใช่ "ยังไม่ทำ"
- เดินจริงใน browser (คลิก แล้วอ่านหน้าจอยืนยัน) **ห้ามอ่านโค้ดแล้วสรุปว่าผ่าน**
- ผลต่อข้อมีได้ 4 ค่า: `pass` / `fail` / `blocked` (ไปจอตั้งต้นไม่ได้) / `n-a` (สเปกไม่ครอบ)
- ปิดท้ายด้วย **coverage**: flow มีกี่ transition เดินได้จริงกี่อัน ตัวเลขนี้บอกว่ารายงานเชื่อได้แค่ไหน

## ส่วน 3: ใช้ Design System จริงไหม (component, token, style)

รันจากถูกสุดไปแพงสุด ตามลำดับ:

1. **component ที่ Design System มี แต่ prototype วาดเอง** เทียบ import ในโค้ดกับรายชื่อ component ของ Design System
   (จาก package, `components.json` หรือ MCP ของ Design System ถ้ามี)
2. **ถ้า Design System มี MCP หรือคำสั่งตรวจโค้ด** (เช่น `verify_code`, `check_coverage`) ให้รันกับไฟล์ที่เกี่ยว ผลระดับ error = defect ต้องขึ้นรายงาน
   ถ้าไม่มี ข้ามข้อนี้แล้วเขียนในรายงานว่าตรวจด้วยข้อ 1, 3, 4
3. **ค้นหาค่าที่เขียนตายตัว**: hex, `px` ดิบ, ชื่อ font ทุกค่าที่ Design System มี token ต้องใช้ token
4. **เลือก component ผิดตัว ร้ายกว่า style ผิด** อ่านคำแนะนำการใช้ของ component (when to use / when not to use) แล้วเทียบกับที่ใช้จริง

### วิธีตัดสินที่ของปลอมผ่านไม่ได้
checklist โดนโค้ดที่วาดเองผ่านได้ แต่ **การสลับโหมดผ่านไม่ได้**:

> ถ้า Design System มีโหมด (เช่น `data-theme`, `data-density`, `data-shape` บน root) ให้สลับแล้ววัด `border-radius`, `padding`, `color` ซ้ำ
> **ค่าไหนไม่ขยับ = ค่านั้นไม่ได้มาจาก token จริง**

CSS ที่เขียนเองนิ่งได้ แต่ตามโหมดไม่ได้

## Output: รายงานอย่างเดียว

เขียนไฟล์ `docs/QA-REPORT-YYYY-MM-DD.md` ในโปรเจกต์ และสรุปสั้นในแชท
รูปแบบเต็มอยู่ที่ `references/report-format.md`

**ระดับความรุนแรง 4 ระดับ:**

| ระดับ | ความหมาย | ตัวอย่าง |
|---|---|---|
| `blocker` | flow ตัน หรือจอที่สเปกมีแต่ไปไม่ถึง | กด Transactions แล้วไม่ไปไหน |
| `error` | ต่างจากสเปกแบบวัดได้ | `padding 20px` แต่ Figma `24` · component ที่ Design System มีแต่วาดเอง |
| `warn` | ต่างนิดหน่อย หรือจับคู่ไม่ได้ | `line-height` ต่าง 0.5px · element ไม่มีข้อความให้จับคู่ |
| `info` | ไม่ใช่ defect แต่ควรรู้ | design สองเฟรมขัดกันเอง |
